# Домашнє завдання 2. Транспортний рівень та служби мережі


> **Середовище виконання:** Ubuntu 24.04 у Docker-контейнері (macOS + Docker Desktop).
> Контейнер «чистий», тому для появи відкритих портів у фоні запущено:
>
> ```
> python3 -m http.server 8080 > /dev/null 2>&1 &
> python3 -m http.server 9000 > /dev/null 2>&1 &
> nc -dlu 5005 > /dev/null &
> ```
>
> Знак `&` запускає процес у фоновому режимі.

---

## Завдання 1. Аналіз відкритих портів

**Команда:**

```
ss -tuln
```

Ключі: `-t` показує TCP, `-u` показує UDP, `-l` залишає лише сокети, які слухають, `-n` виводить номери портів замість назв сервісів.

**Результат:**

```
Netid  State   Recv-Q  Send-Q   Local Address:Port   Peer Address:Port Process
udp    UNCONN  0       0              0.0.0.0:5005        0.0.0.0:*
tcp    LISTEN  0       5              0.0.0.0:8080        0.0.0.0:*
tcp    LISTEN  0       5              0.0.0.0:9000        0.0.0.0:*
```

**Відкриті порти:**

| Протокол | Порт | Стан | Сервіс |
|---|---|---|---|
| TCP | 8080 | LISTEN | локальний веб-сервер (`python3 -m http.server`) |
| TCP | 9000 | LISTEN | локальний веб-сервер (`python3 -m http.server`) |
| UDP | 5005 | UNCONN | UDP-слухач `nc` |

**Пояснення:**
- `0.0.0.0` означає, що сервіс приймає підключення на всіх мережевих інтерфейсах.
- TCP-порти мають стан `LISTEN`, тобто чекають на встановлення з'єднання.
- UDP-порт має стан `UNCONN` (unconnected). UDP не встановлює з'єднань, тому стану LISTEN у нього немає, а сокет просто приймає пакети.

## Завдання 2. Аналіз процесів, що слухають порти

**Команда:**

```
ss -tulpn
```

Ключ `-p` додає інформацію про процес, який відкрив порт (команда виконувалась від root, тому `sudo` не знадобився).

**Результат:**

```
Netid   State    Recv-Q   Send-Q     Local Address:Port     Peer Address:Port   Process
udp     UNCONN   0        0                0.0.0.0:5005          0.0.0.0:*       users:(("nc",pid=2849,fd=3))
tcp     LISTEN   0        5                0.0.0.0:8080          0.0.0.0:*       users:(("python3",pid=2847,fd=3))
tcp     LISTEN   0        5                0.0.0.0:9000          0.0.0.0:*       users:(("python3",pid=2848,fd=3))
```

**Процеси:**

- Процес: `python3`, PID: 2847, порт: 8080 (TCP)
- Процес: `python3`, PID: 2848, порт: 9000 (TCP)
- Процес: `nc`, PID: 2849, порт: 5005 (UDP)

**Пояснення:** PID збігаються з номерами, які видала оболонка під час запуску фонових процесів (`[1] 2847`, `[2] 2848`, `[3] 2849`). Отже, кожен порт відкрив саме той процес, який я запустила. `fd=3` означає номер файлового дескриптора сокета всередині процесу.

## Завдання 3. Перевірка TCP-з'єднання

**Команда:**

```
nc -vz google.com 80
```

Ключі: `-v` вмикає детальний вивід, `-z` лише перевіряє, чи відкритий порт, без передачі даних.

**Результат:**

```
Connection to google.com (142.250.130.102) 80 port [tcp/http] succeeded!
```

- Тип з'єднання: TCP
- Порт: 80 (HTTP)
- Результат: з'єднання встановлено

**Пояснення:** `nc` спочатку визначив IP-адресу google.com через DNS (142.250.130.102), а потім виконав TCP-рукостискання (SYN → SYN-ACK → ACK). Повідомлення `succeeded!` означає, що сервер відповів і з'єднання успішно встановлено.

## Завдання 4. Порівняння TCP vs UDP

**Команди та результат:**

```
nc -vz 8.8.8.8 53
Connection to 8.8.8.8 53 port [tcp/domain] succeeded!

nc -u -vz 8.8.8.8 53
Connection to 8.8.8.8 53 port [udp/domain] succeeded!
```

`8.8.8.8` — публічний DNS-сервер Google, порт 53 — DNS (`domain`). Ключ `-u` вмикає перевірку по UDP.

**Порівняння:**

| | TCP | UDP |
|---|---|---|
| Встановлення з'єднання | так, рукостискання SYN → SYN-ACK → ACK | ні (connection-less) |
| Що означає `succeeded` | сервер відповів, з'єднання точно встановлено | пакет відправлено і не повернулося помилки |
| Гарантія відповіді | є | немає |

**Різниця в поведінці:**
- **TCP:** є підтвердження з'єднання. Результат достовірний, бо сервер сам відповів на рукостискання.
- **UDP:** немає гарантії відповіді. `nc` просто надсилає пакет і, якщо не отримав повідомлення про помилку (ICMP «port unreachable»), вважає перевірку успішною. Тобто `succeeded` для UDP не доводить, що сервер справді отримав пакет.
- **Висновок:** TCP встановлює сесію і гарантує доставку, UDP — ні, зате він швидший і простіший. DNS підтримує обидва протоколи: звичайні запити йдуть по UDP, а TCP використовується для великих відповідей і передачі зон.

## Завдання 5. DNS резолвінг

**Команда:**

```
dig github.com
```

**Результат:**

```
; <<>> DiG 9.18.39-0ubuntu0.24.04.8-Ubuntu <<>> github.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12501
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0

;; QUESTION SECTION:
;github.com.			IN	A

;; ANSWER SECTION:
github.com.		77	IN	A	140.82.121.4

;; Query time: 67 msec
;; SERVER: 192.168.65.7#53(192.168.65.7) (UDP)
;; WHEN: Thu Oct 15 02:47:31 EEST 2026
;; MSG SIZE  rcvd: 54
```

- Домен: github.com
- IP: 140.82.121.4
- DNS сервер: 192.168.65.7

**Пояснення:**
- `status: NOERROR` означає, що запит виконано успішно.
- `QUESTION SECTION`: запитували запис типу `A` (IPv4-адреса) для github.com.
- `ANSWER SECTION`: отримали IP-адресу 140.82.121.4. Число `77` — це TTL, тобто скільки секунд відповідь можна зберігати в кеші.
- `SERVER: 192.168.65.7#53 (UDP)`: відповів DNS-сервер 192.168.65.7 на порту 53, запит пішов по UDP. Це внутрішній DNS-резолвер Docker Desktop, який пересилає запити контейнера до DNS-сервера моєї мережі.
- `Query time: 67 msec`: час отримання відповіді.
